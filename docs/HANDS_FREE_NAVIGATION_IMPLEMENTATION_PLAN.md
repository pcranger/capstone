# CrossWise: hands-free navigation and crossing perception — implementation plan

**Updated 6 October 2026. Status: segmentation-label correction, shared foreground location, automatic voice entry/destination actions and Settings precautions implemented and software-tested. Physical voice/location acceptance is pending. Automatic route-step progress, roadside estimation and autonomous crossing remain unimplemented/unvalidated.**

**User requirement: no routine questions.** Do not ask the traveler to identify a roadside, judge traffic, confirm a kerb, or certify completion. Infer these from qualified observations; otherwise give a concise capability/recovery instruction. User-originated destination/save/pause commands remain available. First-use OS consent remains unavoidable. See the [repository study and scenario assessment](INSTRUCTION_FIRST_RESEARCH_AND_SCENARIOS.md) for evidence, reuse decisions and first-time-user acceptance. A failure to guide autonomously must be recorded as a failed route task, not hidden by asking the user to supply missing perception.

This is the current plan for the user's location, voice, roadside and crossing concerns. It supersedes conflicting proposals in redesign sections 13–14 and earlier crossing roadmaps. Keep the working vehicle detector, camera-first interface, full-screen interactive Google map, bottom destination controls and saved places. Implement and accept one increment at a time.

## 1. Decision and realistic scope

Use existing pretrained components first. Do not train from scratch or replace the whole application. Build automatic foreground location recovery and a deterministic voice journey, while evaluating surface perception and visual localization separately. A useful first release can guide a route and announce crossing preparation without claiming to know the exact kerb, roadside or safe crossing time everywhere.

There are four distinct problems:

1. **Route:** where the destination and candidate pedestrian crossings are.
2. **Localization:** which segment and side the person occupies, with uncertainty.
3. **Local scene:** visible vehicles, road, sidewalk, markings, obstacles and possibly kerbs.
4. **Crossing decision:** live signal relevance, traffic conflicts and the person's movement.

Solving one does not solve the others. A sidewalk mask has no global street identity. A VPS coordinate does not prove a walkable connection. A vehicle detector cannot observe traffic hidden by parked cars or outside the camera view. The app must not convert “nothing detected” into “walk now.”

**Deliverable now:** automatic foreground startup/recovery, concise voice destination-command flow, route progress, and evidence-qualified crossing preparation. **Conditional:** surface observations and roadside estimates on tested routes. **Deferred:** autonomous permission to enter the road, exact crossing step counts, universal roadside localization, and unattended camera operation while the phone is locked.

Current app issues that affect this plan:

- `mobile/src/nav/journey.ts`: `pause()` stops location watching, clears the exposed location and sets location status to waiting. - `mobile/src/camera/CameraSurface.tsx`: one active model plan and VisionCamera capture feed the current detector. Adding a second model or an ARKit capture owner requires deliberate scheduling and image-coordinate verification.
- `mobile/src/voice/audioCheck.ts`: voice currently has a bounded microphone/repeat test, not a complete command dialogue. Physical speech/audio acceptance remains outstanding.

No newly shortlisted candidate was run, converted or benchmarked on the iPhone. On 6 October the existing bundled detectors were rerun on `mobile/read.JPG` on the Mac; the scenario report records the results and limitations. Upstream code, weights, datasets and proprietary SDK terms require separate review before integration; a repository license alone is insufficient.

## 3. User journey and short prompts

The objective is no routine Start/End button for each road crossing. First-use system permissions still require the operating system's accessible consent UI. Returning users should not repeat setup.

| Situation | Behaviour and example wording |
|---|---|
| First ordinary foreground launch | Acquire location and initialize perception quietly. “Welcome to CrossWise. Say your destination after the tone.” Open listening after speech finishes. |
| Existing paused journey | Preserve destination and progress. “Navigation paused. Say resume to continue.” Explicit user pause stays paused until the user commands resume. |
| Ordinary system interruption | Reacquire fresh observations; resume an eligible ordinary route once validated. If interrupted during crossing, invalidate the old crossing estimate, reacquire context and announce unavailable guidance if it cannot be recovered. Do not ask the user to certify their position. |
| Destination given | Search near a qualified location. For an unambiguous explicit “Navigate to Central Library” command: “Navigating to Central Library, King Street.” A plain search does not authorize starting. Do not select an ambiguous result silently. |
| Multiple matches | “Two matches. Say the place name and suburb.” This requests destination intent, not environmental judgment. Support a user-originated selection and cancel; never manufacture a destination. |
| Save place | Support “Save as Home,” then “Saved as Home.” A plain save uses the selected place’s existing name without a follow-up question. “Save” applies only to the current selected place; saving does not start navigation. |
| Location not yet usable | Let destination dialogue continue where possible. Say “Finding your location” once when it blocks routing, not repeatedly on every update. |
| Walking | Speak a turn when needed; silence during uncomplicated progress. “Turn left at King Street.” Approximate map distances remain approximate. |
| Candidate crossing approaching | “Crossing ahead.” Preparation is triggered only once per approach, with a route/context confidence gate. |
| At a suitable observed scanning position | “Hold the phone upright.” Then, when needed, “Scan slowly left, then right.” Do not instruct someone to approach an unverified kerb merely to improve the camera view. |
| Visible traffic | “Car on your left.” Use “approaching from the left” only after validated motion/coordinate reasoning. Prefer actionable changes over repeated object lists. |
| Occluded or poor view | “View blocked.” or “Camera view unclear.” Absence of detections produces no clearance claim. |
| Crossing underway | Suppress destination chatter. Prioritize qualified hazard observations; do not issue speculative stop/turn commands from a weak mask. |
| Completion uncertain | Determine the far sidewalk from temporal pose, topology and scene evidence, distinguishing islands. If unresolved, announce “Position tracking lost. Direction guidance unavailable.” Do not auto-complete, ask a question, or infer that stopping in the carriageway is safe. |
| Arrival | “You have arrived at Central Library.” Stop route guidance; do not assert the exact entrance unless verified. |

These are proposed prompts, to validate with users and actual audio. No environmental yes/no dialogue is planned. Each command is scoped to the current task and expires when context changes. Use one actionable instruction at a time, and issue a listening tone only when accepting a user command. Never announce a command before its handler exists.

## 4. Architecture with explicit evidence boundaries

**LocationCoordinator:** one owner for permissions, last-known position, foreground watch, freshness and quality. Consumers include map, journey and roadside estimator. Distinguish cached/approximate/fresh/unavailable; display a cached map position without allowing it to drive crossing guidance. Subscribe at an appropriate rate for active navigation; stop unnecessary high-rate work. Separate location acquisition from route narration pause.

**VoiceCoordinator and DialogueState:** bounded listening turns, intent/slot parsing, context and cancellation tokens. Actions call the same destination/saved-place/navigation services as touch. Start with a constrained command vocabulary, not a general language-model action executor. Coordinate TTS, recognition, VoiceOver, audio focus and Bluetooth. “Cancel,” “pause,” “resume,” “repeat,” “help” have explicit state-dependent meanings.

**RouteContext:** combines Google walking route progress with separately sourced pedestrian topology. Crossing candidates retain source IDs, geometry provenance, update time and confidence. Do not assume Google instructions enumerate every crossing or snap automatically to the nearest OSM crossing. Reconcile by connected path, direction and route segment; return unknown for conflicting data.

**Perception adapters:** keep vehicle detection independent from surface inference. Each model has a manifest defining labels, tensor layout, color order, normalization, resizing, output decoding, checkpoint hash and runtime. Dense semantic masks and YOLO instance masks are separate formats. Unsupported categories stay unknown.

**Pose and RoadsideEstimator:** maintain candidate sidewalk/road segments and evidence, not a forced binary left/right choice. Distinguish camera-relative left/right, travel-relative left/right, OSM way direction, and geographic position. Each observation carries frame/time/reference-frame identity and quality. Relative inertial yaw can maintain local continuity but needs an independently verified alignment to geographic coordinates.

**CrossingCoordinator:** a state machine: ordinary route → candidate approach → preparation → observation → crossing underway → completion check → ordinary route. Unknown, interrupted and cancelled are explicit states. Different evidence gates control approaching a crossing, observing traffic and recognizing movement. No transition named “safe because clear.”

**PromptArbiter:** interrupts routine speech for qualified hazards, suppresses duplicates, expires stale messages, and limits voice traffic. Model-loaded/debug messages belong in Developer mode. Do not announce an old detection after the user turns the phone.

**Capture ownership:** the existing VisionCamera path remains the baseline. Test ARKit/ARCore in a separate diagnostic first. If selected, design one native capture owner feeding preview, YOLO, semantic observations and pose with synchronized transforms. Do not start competing ARKit and VisionCamera sessions. A camera migration must pass the current vehicle box-alignment and motion tests before adoption.

## 5. Roadside localization: when it can actually work

GPS alone is insufficient when its uncertainty overlaps both sidewalks. Illustratively, two candidate paths 8 m apart cannot be reliably distinguished by a position reported with 10 m horizontal uncertainty. Accuracy radii are estimates, not hard bounds; map errors add further uncertainty.

Use a staged approach:

1. Build a small surveyed pilot-route graph with explicit sidewalk/crossing connections, including islands and driveways. Retain OSM tagging provenance. Verify the local map rather than assuming all infrastructure is mapped.
2. Track multiple feasible positions along that graph using location, route history and motion. Avoid snapping a stationary person to a side based on small GPS changes.
3. Collect camera-relative road/sidewalk evidence only when pose and visibility support the observation. Seeing road on the left does not determine global roadside without orientation and segment identity.
4. Establish side automatically from map connectivity, aligned pose and qualified scene/landmark evidence. Do not ask a contextual landmark or left/right question. If side remains ambiguous, keep that estimate unknown and withhold dependent direction commands. Explain the unavailable function once and attempt bounded recovery without directing speculative movement.
5. Evaluate VPS on both sides of the same street. Check availability, actual localization success, yaw, elapsed time, uncertainty and observed error. Availability alone is not localization success. Require discrimination between competing sidewalk hypotheses, not Google's sample high-accuracy boolean.
6. Invalidate or reduce confidence after turns, pose reset, stale GPS, inconsistent visual evidence or map ambiguity. Do not preserve a confident side indefinitely from an old observation.

Streetlights, traffic-signal map tags and live pedestrian signals are different things. Map presence can help identify infrastructure; it supplies neither live permission nor proof that the observed signal controls this crossing. Crossing islands are separate stages, not automatic arrival at the destination sidewalk.

## 6. Model evaluation before training

**Experiment A — compact independent baseline:** retrieve a verified PIDNet-S Cityscapes checkpoint, record its hash/terms, validate complete loading, and reproduce its preprocessing. Evaluate original inference on local pedestrian-view images before conversion. A Cityscapes sidewalk label does not mean a path is unobstructed, accessible or connected.

**Experiment B — native alternative:** run an isolated ARCore iOS diagnostic. First check Scene Semantics support and verify mask orientation/confidence. Test semantics and Geospatial separately so a VPS failure does not get misdiagnosed as a segmentation failure. Measure concurrent resource demand if both are useful. General Maps configuration does not automatically enable ARCore services; provision needed computer-side configuration with restricted credentials and document network/data behaviour.

**Experiment C — richer reference, optional:** use a Mapillary-trained OneFormer model offline if execution is practical. Compare class coverage and failures, with manually checked annotations. Do not make running this large model a prerequisite for location/voice work.

Choose the lowest-complexity candidate that meets target-view and device gates. If neither A nor B is useful, stop production integration and report the observed failure modes. Fine-tune a compact model only after establishing whether the problem is viewpoint/domain shift, missing labels, preprocessing or runtime conversion. Missing kerb/crosswalk classes require an appropriate pretrained head or labelled training data; changing the class name is not training.

For conversion, compare original and exported outputs on identical fixed frames, including class IDs, masks, confidence and transforms. Test FP32/FP16 before quantization. Do not assume a successful export means equivalent predictions. Choose Core ML or TFLite according to measured operator support and performance; the existing YOLO loader is not a generic model runtime.

## 7. Data and acceptance protocol

Start with a pilot set of roughly 12 distinct sidewalk segments and 6 crossings, covering both directions and both sides where practical. This is an engineering starting set, not evidence of population-wide reliability. Include narrow/wide streets, driveways, unmarked crossings, refuge islands, parked-car occlusion, shadows, worn paint, bright light, poor light, ramps, phone tilt and motion blur. Record the actual supported conditions.

Split by location and recording session/day, not adjacent frames. Keep a sealed hold-out set. Manually annotate road/sidewalk and the relevant crossing/kerb evidence; mark uncertain ground truth instead of forcing labels. Capture evaluation recordings from safe observation positions with a sighted tester/observer; do not ask a blind participant to rely on an unvalidated prototype in traffic.

Report these separately:

- Road falsely labelled sidewalk, sidewalk recall, boundary error and class IoU. Aggregate IoU alone can hide dangerous local errors.
- Confident wrong-side decisions, unknown rate, time to establish side and recovery after resets. Report both accuracy and coverage so always saying unknown cannot appear successful.
- Incorrect crossing preparation, missed candidates, repeated prompts, false route advances and interrupted-crossing recovery.
- Vehicle/motorcycle recall and box alignment compared with the working baseline; camera panning must not be mistaken for vehicle motion. Keep detection of stationary objects even when prioritizing moving-vehicle speech.
- Speech task completion, unintended actions, TTS self-recognition, noisy-street recognition, VoiceOver/Bluetooth behaviour and recovery from denial/interruption.
- End-to-end observation age, median/p95 inference latency, dropped frames, memory, thermal state and battery use during a sustained 20–30 minute foreground walk simulation/test.

Before measuring candidates, freeze explicit thresholds and the test set. Initial **engineering gates**, not safety certification: no false confident roadside/crossing claims in the release regression set; all stale/ambiguous/reset cases must abstain; no incorrect voice action in ambiguity/cancellation tests; no vehicle-quality regression on the same clips. For performance, measure the current device baseline first and require no more than a provisional 10% p95 vehicle observation-latency regression, with no sustained serious thermal state. Revisit this budget if the baseline itself is inadequate; report absolute times as well as percentages.

Surface inference should begin throttled (trial 2–5 Hz), with latest-frame scheduling and bounded work; tune from measurements rather than promising a fixed rate. Vehicle perception has priority. Expire old observations using a measured, documented latency budget. Suppress surface guidance on overload instead of building a backlog. Zero failures in a finite set is a release gate, never proof of safe autonomous crossing.

## 9. Reassessment and stop rules

After every increment or experiment, record: hypothesis, exact code/model/device version, dataset or route, predicted outcome, observed result, failure examples, and decision (keep/change/defer). Update this plan when evidence changes; never move a failed acceptance threshold quietly to fit a preferred model.

| Uncertainty | Evidence that resolves it | Fallback |
|---|---|---|
| Speech works in street noise without self-triggering | On-phone audio/VoiceOver/Bluetooth test | Accessible touch/VoiceOver controls; do not advertise complete hands-free operation until passed. |
| GPS/visual pose can distinguish sidewalks | Repeated opposite-side surveyed tests with reported uncertainty | Roadside unknown; bounded automatic recovery; announce dependent guidance unavailable. Count the autonomous route task as failed if intervention is needed. |
| Native semantic API fits this iPhone | Runtime capability and sustained measured test | Independent compact segmenter or defer surface guidance. |
| AR capture can preserve YOLO behaviour | Same-scene alignment and motion replay plus device profiling | Keep existing VisionCamera capture; defer AR production integration. |
| Public map represents the crossing correctly | Surveyed pilot graph versus map and route | Mark candidate unverified and avoid precise approach/completion claims. |
| Pretrained model transfers to handheld pedestrian view | Location-held-out mask/error analysis | Fine-tune targeted classes after fixing pipeline errors; no training from scratch by default. |
| Continuous voice activation is practical | Separate wake/listening, power, privacy and false-trigger experiment | Automatic bounded conversational turns; do not describe this as an always-listening wake-word assistant. |

Outstanding field inputs are the pilot neighbourhood/route, actual iPhone audio acceptance, and supervised route observations. These do not block software planning or location lifecycle work. ## 11. 6 October implementation: location and voice entry

The user's updated UX requirement is to put general precautions in Settings and make daily guidance concise. Implemented
increments 1–3 together at their shared location/audio/planner boundary, without changing vehicle weights or enabling
unvalidated automatic crossing transitions. This is a device-test candidate, not acceptance of the full journey plan.

### Behaviour now implemented

- Removed the app-specific first-launch acknowledgment gate. General limitations, model limitations and stereo-tone
  information are in Settings. Immediate missing-camera/location/recognition states remain actionable messages.
- Retained one short, unspoken Google walking-route notice with each displayed route because the provider
  [requires it](https://developers.google.com/maps/documentation/routes/route-opt). This is the exception to moving all
  precaution text into Settings; it creates no acknowledgment step.
- A single foreground location owner starts after camera consent, feeds the map independently of route pause, expires
  stale fixes, reconnects a failed native watch, and ignores callbacks from stopped generations. In-memory/cached fixes
  do not qualify navigation until a fresh usable native fix arrives. Approximate positions are not presented as precise.
- An OS-interrupted ordinary journey reacquires location before resuming. An explicit Pause remains paused, and an
  unfinished crossing cannot auto-resume. Backgrounding stops route consumers before stopping GPS, avoiding a spurious
  location-loss instruction during the transition.
- Automatic startup says “Welcome to CrossWise. Say your destination after the tone.” Voice resolves destinations,
  starts an unambiguous requested route, reads up to three ambiguous results, saves aliases and handles repeat,
  pause/resume/end/cancel/retry/help. Search alone does not start a journey. Touch and voice use the existing planner.
- Speech and microphone turns are serialized using native completion, not a fixed delay. Cancellation invalidates late
  recognition/network results. Silence timeouts rearm quietly, and traffic/signal announcements interrupt recognition.
  Switching to touch clears any pending voice intent to automatically start navigation.

### Reassessment and changes made during review

| Failure examined | Change / decision |
|---|---|
| Pausing the route erases the map location | Separate location ownership from route consumers; keep foreground fixes when paused. |
| A stationary user receives no GPS refresh | Remove the native distance filter; retain freshness and accuracy validation. Test actual iPhone cadence outdoors. |
| Camera/location consent requests overlap on first launch | Defer initial location acquisition until the camera permission step completes. |

| Switching to touch retains an earlier “navigate to” intent | Clear voice auto-start intent on explicit voice stop/touch takeover. |
| Silent microphone timeout produces repeated prompts/tones | Quietly rearm; readiness tone only on initial listening or after a spoken response. |
| Permission description says “after tapping Voice” | Updated the Expo config and regenerated iOS metadata for automatic foreground voice. |
| Removing manual completion would leave route progression stuck | Keep existing controls until replay-tested automatic progress replaces the transition. Do not claim the whole journey is hands-free yet. |
